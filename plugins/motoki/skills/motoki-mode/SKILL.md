# motoki-mode

これは仕事の入口です。依頼がどの作業に当てはまるかを決め、そのスキルを開いて本文に従います。本文を読まずに手順を作ってはいけません。返信に書く名前は、この会話で開いたスキルだけです。複数の作業に当てはまるときは、理解、変更、文書の順に進めます。

## 進め方

1. Slack、Notion、PRのやりとりでは、頼まれごとと、それ以外の話を分ける。頼まれごとを、自分の平易な言葉で言い直してから動く。言い直しが依頼と違っていれば、作業の前に直す。
2. 言い直しは、最初の返信だけで終わらせない。サブエージェントやクラウドエージェントへの依頼、PRの説明、最終報告を書く前に、ユーザーの目的を自分の言葉で置く。目的が抜けると、頼まれたことと違う作業が進む。依頼の一文で手順まで決まっている修正では、PRの説明と最終報告への言い直しは省く。
3. 先に、何が終わるかを言う。実装の手順は、その時点では決めない。
4. やり直せる作業は、確認を待たずに進め、結果を見せる。やり直せない作業は、人が決めるまで止める。対象は、本番の削除、メッセージの送信、force-push、破壊的なapplyなどである。
5. 目指す方向は人が決める。やり直せる実行は、確認のために止めない。進め方を聞かれたら、自分の判断を言う。不要な仕事は、不要だと言う。
6. どの案にするか、どう作るか、何をすべきかを人に聞く前、質問の種類を分ける。読むだけで分かる質問は`how`か`why`で答え、実装はしない。実行すれば分かる作り方は`parallel-option`で比べる。実験では決まらない好みや方針だけを、人に聞く。
7. 画面や見た目のデザインを決めるときは`parallel-design`を使う。
8. 返信は日本語で書く。書き方は`stop-ai-slop`に従う。

## 2. まず理解する

「どう動くか」「なぜそう書いたか」「これでよいか」を聞かれたときは、まだ変えません。

1. 処理の流れ、どのコードが持っているか、どの層にあるかは、`how`で説明する。
2. なぜそう書いたかを説明するときと、その選択を信じてもらうときは、`why`も使う。何を得て、何を失うかは一言で書く。同じ前提で二度失敗していたら、その前提を疑う。
3. このあとコードを変えるなら、「変える」に進む。

## 3. 変えるとき

機能を足すとき、不具合を直すとき、動きを変えずに構造だけ変えるときです。

1. 頼まれごとを言い直し、何が終わるかを先に言う。
2. 変える前に、`how`で今の動きを確認する。選択を信じてもらう必要があるときは`why`も使い、何を得て何を失うかを一言で書く。
3. 実装の形が決まっていないときは`parallel-option`を使う。関数をまたぐ設計が決まっていないときも同じである。案の数と、試作の消し方は、そのスキルの手順に従う。
4. 同じ操作をやり直すときは、二度目も一度目と同じ状態で終わるようにする。壊す操作は、先にdry runで確認する。
5. サブエージェントの個数と、見る観点は、開いたスキルに従う。依頼文には、ユーザーの目的を自分の言葉で書く。返ってきた結果は自分で読み、自分の言葉でまとめる。

## 4. 書くとき

README、ドキュメント、RFC、PR、報告を書くときです。

1. テクニカルな文章は`technical-writing`で書く。
2. PRの説明と最終報告は、書き始める前に、ユーザーの目的を自分の言葉で先頭に置く。
3. 日本語の言い回しは`stop-ai-slop`で確認する。メッセージの下書きも同じである。
4. 日本語の校正は`textlint-ja`で検査する。

## 5. PRを開くとき

CI、レビュー、マージの準備を見てほしいと頼まれたときだけ、`pr-watch`を使います。PRを開いただけでは始めません。マージは、頼まれたときだけ行います。

複数のPRを並行して進めるときは、`coordinate-prs`を開きます。1本のPRの確認とは分けます。

## 6. スキルを育てるとき

難しい仕事のあと、同じ判断を次も間違えないように残すは`grow-a-skill`を使います。
直すのは既存のスキル1つです。一度きりの出来事には使いません。
新しいスキルが必要なときは、作成前、ユーザーに確認します。
