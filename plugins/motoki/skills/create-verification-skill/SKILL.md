# 検証スキルを作る

本格的なプロジェクトには、本物のアプリを動かして動きを証明する、手順化された方法が要ります。アプリを起動し、利用者と同じやり方で機能を試し、証拠を残します。このスキルは、それをリポジトリ専用のスキルとして作ります。置き場所は`.cursor/skills/verify-<app>/`です。出力の読み手は人ではありません。次のエージェントです。アプリを見たことがないエージェントは、作業の途中で、何も知らないまま読みます。

## 1. 利用者ではなく、リポジトリに聞く

次の問いは、コードベースから答えます。観測できないことだけ、利用者に聞きます。

- 触る面は、利用者が実際に触るものをコードから答えることである。候補は同列である。Web UI、CLI/TUI、デスクトップアプリが候補である。API、モバイルアプリ、ライブラリも候補である。リポジトリに複数あるときは、主なものを選ぶ。残りは書き残す。
- 起動方法は、アプリをローカルで起動する方法である。リポジトリ自身が文書化した開発用コマンドを優先する。例は、package scripts、Makefile、READMEのquickstartである。ポート、環境変数、初期データ、認証も書き残す。
- 操作手段は、エージェントがプログラムから触る方法である。先に既存のハーネスを探す。PlaywrightやCypressのスペック、expectスクリプト、PTYヘルパーである。curlできるエンドポイントと、デバッグポートも候補である。その後で汎用の手段を選ぶ。WebとElectronはブラウザかCDPである。CLI/TUIはtmuxかPTYである。サービスは素のHTTPである。
- 観測は、証拠として残せるものである。スクリーンショット、端末の記録、レスポンス本文である。ログ、終了コード、DBの状態も残す。
- 分離は、2つのインスタンスを並べて起動できるかの判断である。ポート、データディレクトリ、プロファイルを見る。並べて起動できないときは、生成するスキルに拒否の規則を書く。共有インスタンスの二重操作は拒否する。二重操作は、利用者のセッションを壊す。

チェックアウトしただけではビルドできない、または起動できないときは、生成の前に直すか、失敗した箇所を正確に報告します。壊れた土台に合わせたスキルは、誤った手順を教えます。アプリの動作と無関係な不足が起動を止めているとき、生成するスキルはその不足を検証用の足場として作ってよいです。対象は、APIが配信しない静的ディレクトリや、無いサンプル設定です。生成するスキルに、足場だと明示し、片付けで消すと書きます。

## 2. スキルを書く

`.cursor/skills/verify-<app>/SKILL.md`を書きます。YAMLフロントマターに`name: verify-<app>`を置きます。`description`には、アプリ名、触る面、いつ使うかを書きます。フロントマターが無いスキルは登録されません。各節は、インタビューで分かった事実に基づけます。プレースホルダは残しません。

- 起動では、検証でアプリを起動する正確なコマンドを書く。準備完了の見分け方も書く。ログの1行や、プロンプトである。空のデータディレクトリから、使える状態まで到達する。マイグレーションと初期データも含む。準備完了とは、プロセスが応答することではない。使えることである。DBのヘルスチェックは、初期化スクリプトの完了を意味しない。終了手順も含める。短命なCLIやTUIには、生かし続けるサーバーはない。バイナリのビルドか依存の導入を1回行う。その後の各操作は、その操作だけのPTYセッションか、その操作だけのtmuxセッションで始める。
- 診断では、「このインスタンスを操作する価値があるか」に答える、読み取り専用の確認を1つ置く。プロセスが起動している。バージョンかビルドが正しい。ポートを持っているのは、この実行である。認証が有効である。様子がおかしいとき、エージェントは最初にこれを実行する。
- 操作では、ハーネスの手順に、このリポジトリの実在するセレクタとコマンドを書く。例示は書かない。座標やタブ順より、安定した手がかりを優先する。ARIAラベル、data属性、プロンプト文字列、ルートのパスである。
- 証拠では、証明のために残すものと、置く場所を書く。証明の基準も書く。内部のセッターや、テスト専用エンドポイントは使わない。本物の利用者の経路をたどる。最終画面だけでなく、操作と、その結果の状態を残す。見えるものに加えて、副作用を確かめる。書いたファイル、挿入した行、送ったメッセージである。モックは、本番の境界がすでに外部システムを切り離している箇所だけに使う。安全な経路がドライランやテストモードなら、その名前を信じない。省略しているものを、観測で確かめる。見る対象はファイル、ネットワーク、gitの参照である。ドライランという名前でも、ネットワークに触るものがある。ブラウザを開くものもある。
- 片付けでは、この実行が作ったインスタンスの止め方を書く。プロセス名では止めない。自分で起動したものだけを止める。片付けが消すのは、インスタンスと作業用の状態である。証拠は消さない。証明の成果物は、スキルが名指しした場所に残す。
- ヘルパーでは、スキルが同梱するスクリプトを、実行可能にする。呼び出し方は本文に示す。読者が逆算しないと使えないものは、ヘルパーではない。

## 3. 機能マップの初期ファイルを作る

`.cursor/skills/verify-<app>/features/README.md`を作ります。識別できた利用者向け機能ごとに、ファイルを1つ作ります。最初は上位の3件から5件を目安にします。ルート、コマンド、メニュー、ドキュメントから拾います。作るのは、READMEの索引と、機能ごとの1ファイルです。各ファイルは、利用者の視点で、機能が何かに答えます。どう到達するかにも答えます。ハーネスでどう操作するかにも答えます。動いたと分かる終了状態が何かにも答えます。H2は4つです。順に`下位機能`、`到達方法（利用者の視点）`、`<ハーネス>での操作`、`注意点`です。手順が必要とする前提が初期データに無いとき、その手順は失敗として報告します。理由は、その機能の`注意点`に書きます。通すために、手順を弱めてはいけません。マップは、リポジトリが保守する検証の正本です。マップが他の入口も挙げているのに、通りやすい入口だけを操作した証明は不完全です。

## 4. 渡す前に、生成したスキルを証明する

生成したスキルの手順を、端から端まで1回実行します。起動します。診断します。マップした機能を1つ操作します。1つで足ります。マップは、後の実行が残りを扱うためにあります。証拠を残します。片付けます。片付けのあと、名指しした場所に証拠がまだあることを確認します。証明を消す片付けは、この段階の失敗です。失敗した箇所は直します。失敗した試行のあとにも、生成した片付けを実行します。壊れた試行が、プロセスとポートを残さないようにするためです。実行したことがない生成スキルは、成果物ではありません。下書きです。本物の対象の代わりで証明したときは、準備をすべて列挙します。列挙するのは、代わりだけが行う準備です。対象が行わない準備です。代わりとは、新しいVMの代わりのコンテナや、リモートの代わりのローカル構成です。それらの準備は、本物の対象で同じように準備するまで未検証です。

## 5. 保守のループを案内する

アプリの変化に合わせてマップを正しく保つため、利用者に`/maintain-verification-skill`を案内します。周期は、聞かれたときだけ提案します。
