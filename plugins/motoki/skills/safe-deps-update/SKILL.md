# safe-deps-update

ライブラリのアップデートを確認して反映を提案します。

## 入力

次が揃うまで、更新は始めません。決め打ちすると、別のリポジトリを更新してしまうためです。

- リポジトリ。形式は `owner/name`
- 本番URLと、確認すべき公開画面の範囲

## Step 1: Renovateで依存の状態を見る

渡されたリポジトリのデフォルトブランチを、作業ディレクトリに取り出します。
そのルートで、次を実行します。メジャーを固定します。固定しないと、非サポートの Renovate 37 が入ることがあります。

```bash
LOG_LEVEL=debug LOG_FORMAT=json npx --yes renovate@44 --platform=local --require-config=ignored --onboarding=false
```

標準出力の JSON 行だけを使います。npm の警告行は無視します。作業ツリーに差分が出たら、調査の結果としては使わず、元に戻します。

## Step 2: 差分を特定する

ログから、メッセージが `packageFiles with updates` のオブジェクトだけを読みます。各依存で使う項目は次です。

- `depName`
- `lockedVersion`（いま入っている版。`package.json` の範囲ではない）
- `updates[].updateType`
- `updates[].newVersion`
- `skipReason`（`updates` が無いとき）

破壊的変更かは Release Notes で判断します。Release Notes がログに無いときは、そのパッケージの GitHub Releases か changelog を読みます。

`updates` が複数あるときは、各要素を別の更新として扱います。
同じパッケージの、現行範囲の最新と最新メジャーを1行にまとめません。出力する版は、どちらも `lockedVersion` と `newVersion` です。

Renovate は、現行範囲の最新と、最新メジャーだけを出します。
その間のメジャーは、実行環境のバージョンと一致するものだけ追加で調べ、同じ規則で分類します。
例として、Node 24 で `@types/node` の候補が 22 と 26 だけのとき、24 を追加で見ます。

`skipReason` がある依存は分類しません。調査結果の末尾に、未調査として `depName` と `skipReason` を書きます。
GitHub Actions が `github-token-required` のときは、未調査のまま残します。

`No vulnerability alerts found` は、脆弱性が無いという意味ではありません。
この実行形態は GitHub の脆弱性アラートを見ません。脆弱性は次で別途確認します。

```bash
npm audit --json
```

Critical は、advisory ごとに脆弱な範囲と `first_patched_version` を読みます。
`npm audit` がパッケージ全体に付けた範囲は使いません。修正版が現行メジャーの中にあるかは、その件の修正版で判断します。

直接依存を上げても、ロックが脆弱な版のまま残る optional や transitive は、その直接依存と同じ更新に含めます。

### 分類

各更新を、次の順で最初に一致した欄へ入れます。1つの更新は1つの欄だけです。

1. 本番に届く Critical で、現行メジャー内に修正版があるものを、反映するべきに入れる
2. `updateType` が `major` であるか、Release Notes に破壊的変更があるものを、見送るべきに入れる
3. 残りを、様子見して良いに入れる

本番に届くとは、本番で動くプロセスがその依存を読み、リポジトリのコードが脆弱な経路を呼んでいることです。開発依存で、本番の起動にもビルド成果物にも含まれないものは届きません。届かない Critical は 1 に入れず、2 か 3 に進みます。

届くかどうかは、コードで確認したことと、ファイルから推定したことを分けて書きます。

セキュリティ修正が現行メジャーと最新メジャーの両方にあるときは、現行メジャー側を 1 で、最新メジャー側を 2 で分類します。見送る理由に、修正は現行メジャーに入っていると書きます。

実行環境と一致しないメジャーは 2 に入れます。例として、ランタイムが Node 24 のときの `@types/node` 26 です。

### 破壊的変更

見送るべきに入ったものについて、必要なコード修正を Release Notes から書きます。

### 機能追加

Release Notes の新しい機能のうち、バージョンを上げるだけでは有効にならず、コードで使い始める必要があるものを探します。

このリポジトリの価値を、自分の言葉で言い直します。その価値に直接効く機能だけを、Step 3 の機能追加の提案に書きます。効かない機能は提案しません。反映するべき、様子見して良い、見送るべきには、機能の説明を書きません。

## Step 3: 調査結果の出力

版はロックされた版で書きます。同じパッケージの更新が複数なら、欄をまたいで別項目にします。

```markdown
## 反映するべきもの

A1: supabase-js 2.1.0 -> 2.1.1
反映するべき理由を常体で書きます。届くと判断した経路と、推定が残る点を分けて書きます。

## 様子見して良いもの

B1: xxxx x.y.z -> x.y.z+1
様子見して良い理由を常体で書きます。

## 見送るべきもの

C1: xxx x.y.z -> x.y.z+1
見送る理由を常体で書きます。破壊的変更では、必要な修正を書きます。

## 機能追加の提案

このリポジトリの価値を、言い直した1段落で書きます。

D1: XXXのYYYを導入する。
導入して得られる価値を常体で書きます。

価値に効く機能が無いときは、項目を作らず「提案なし」と書きます。見た機能のうち、価値に効かなかった名前を1行ずつ添えます。

## 未調査

E1: actions/checkout
skipReason を書きます。
```

## Step 4: ブランチと PR を開く

ユーザーからの回答を受けて、入れてよい更新があるときだけ、エージェントに作業を開始させます。
コード変更を伴わない変更は1つにまとめます。
コード変更が必要なものは、それぞれ別々のPRで対応します。ただし、依存関係がある場合は、それらの依存を含めて1PRにまとめます。
